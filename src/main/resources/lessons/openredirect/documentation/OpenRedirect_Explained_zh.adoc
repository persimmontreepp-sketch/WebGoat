== 什么是开放重定向？

image::images/redirect-flow.svg[Open Redirect Flow,align=left]

[subs=+quotes]
____
用户 --> *可信网站*（/redirect?url=...）--> HTTP 302 Location：攻击者网站 --> 用户的浏览器现在打开恶意页面。
____

当应用获取用户可控的值（查询参数、表单字段、片段或路径段），并在未对最终目标进行*严格验证*的情况下使用它来构建重定向响应（通常为 HTTP 302/303/307），就会发生开放重定向。

=== 为什么重要

虽然开放重定向**不会**直接执行攻击者代码，却能有效地*放大钓鱼攻击*并*借用信任*：

* 用户先看到合法域名，点击链接后却被透明地转发到恶意网站。
* 如果验证薄弱，OAuth/SSO 和联合登录流程有时会将授权码或令牌泄露到攻击者控制的重定向 URI。
* 有些安全扫描器和过滤器对以危险载荷为终点的重定向链与直接请求采取不同处理，攻击者因此可以绕过简单防御。

=== 常见参数名

请留意以下常被滥用的参数名（包括大小写和分隔符变体）：

[cols="1,3"]
|===
|参数 |用途
|`returnUrl`、`return`、`r` |登录后继续跳转或深层链接
|`next`、`nxt`、`continue` |身份验证/购买流程完成后继续
|`redirect`、`redirectUrl`、`redir` |通用跳转端点
|`dest`、`destination`、`target`、`to` |营销/跟踪链接
|`go`、`url` |简写参数
|`callback`、`cb` |OAuth/API 风格的回调目标
|===

=== 薄弱（不安全）的验证模式

* 子串检查：`if (url.contains("mycorp"))`——会允许 `mycorp.attacker.com`。
* 仅检查原始字符串前缀：`url.startsWith("https://portal.mycorp.com")`——可通过用户信息字段绕过：`https://portal.mycorp.com@evil.com`。
* 验证前只解码一次：双重编码会隐藏危险字符，直到后续处理时才显现。
* 允许协议相对格式：`//evil.com` 会沿用当前协议。
* 盲目追加路径：`"https://portal.mycorp.com" + userValue`——如果 `userValue` 以 `//evil.com` 开头，某些用户代理会将目标更改为恶意网站。

=== 攻击思路与利用步骤

. 通过浏览页面、拦截代理或模糊测试找到重定向参数。
. 提供主机名明显不同的绝对 URL，观察服务器是否会以 302 状态码跳转。
. 如果被阻止，尝试以下绕过方法：
.. 在攻击者主机名中加入可信域名子串（`trusted.com.evil.net`）。
.. 注入用户信息字段（`trusted.com@evil.net`）。
.. 对关键字符进行双重编码（`%2540` -> `%40` -> `@`）。
.. 尝试协议相对 URL：`//evil.net/path`。
.. 如果缺少规范化处理，尝试大小写、尾部句点或 Unicode 形近字符技巧。
. 链接攻击或升级攻击：与 OAuth 开放重定向组合以窃取授权码，或构造有说服力的钓鱼链接。

=== 现实中的影响场景

* *窃取凭据*：钓鱼电子邮件先使用合法域名：`https://bank.example/invite?returnUrl=https://bank.example.login-reset.attacker.site`。
* *令牌泄露*：配置错误的 OAuth 重定向 URI `https://app.example/redirect?next=https://evil.site` 可能会在中间页面反映授权码时将其转发。
* *绕过过滤器*：WAF 规则允许第一个跳转目标，然后通过跳转链抵达最终漏洞利用服务器。

=== 更安全的设计模式

* **严格允许列表**：使用可靠的 URI 库解析 URL，并将完整主机名和可选端口与常量集合进行精确比较。
* **ID/令牌映射**：客户端发送 `destId=3`，服务器在内部将其映射到 `/user/profile`；绝不直接接受外部 URL。
* **仅允许相对路径**：拒绝所有绝对 URL，仅接受经过验证、规范化和标准化的相对路径。
* **规范化**：将主机名转换为小写，删除尾部句点，在验证前以*有界且防御性*的方式重复解码，然后如果解码会改变分类，就拒绝请求。
* **上下文隔离**：不要在 HTML/JS 中原样反映用户提供的 URL（以防止通过组合方式引发 XSS/社会工程攻击）。

=== 快速手动测试清单

[ ] 参数是否接受绝对 URL？
[ ] 主机过滤逻辑是什么？子串/前缀/正则表达式？
[ ] 对用户信息字段 `@` 的处理如何？
[ ] 对双重编码 `%252F`、`%2540` 的处理如何？
[ ] 是否接受协议相对 URL？
[ ] 是否接受混合大小写/尾部句点主机名？
[ ] 重定向状态码（301、302 或 307）是否一致？
[ ] 是否保留查询片段（可能导致开放重定向和令牌泄露）？

=== 本课程与现实场景的对应关系

* 任务 1：完全不安全——任意外部主机均可使用。
* 任务 2：朴素的子串过滤器。
* 任务 3：前缀检查没有验证解析后的主机名。
* 任务 4：只解码一次再进行验证，第二次解码会改变语义。
* 防护页面：展示允许列表和 ID 映射原则。

请将这些思路牢记于心；现实攻击会将细微的规范化缺陷与误导性用户体验组合起来，利用用户信任。
