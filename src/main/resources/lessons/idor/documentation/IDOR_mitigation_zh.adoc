== 安全对象引用

=== 从目标状态开始设计
你是否记录了访问控制规则？如果没有，如何确保规则得到实施？访问控制由应用业务逻辑以及隐私和其他法律所决定。

==== 横向和纵向访问控制
我们经常按“角色”（用户、高级用户、管理员等）来考虑访问控制。
不过，正如前面的练习所示，拥有相同“角色”的用户也可能访问彼此的数据。这就是横向访问控制。两种访问控制都必须实施。

.访问控制矩阵示例
|===
|端点 |方法 |说明 |角色、访问规则 |备注、注意事项

| /profile
| GET
| 查看用户个人资料
| 已登录用户只能查看自己的个人资料
| 管理员必须使用不同 URL 查看他人资料（见下文）

| /profile/{id}
| GET
| 查看指定用户的个人资料
| 已登录用户可以通过 {id} 查看自己的个人资料，管理员也可以查看
| 不适用

| /profile/{id}
| PUT
| 编辑用户个人资料。客户端在请求中提交个人资料对象
| 已登录用户可以通过 {id} 编辑自己的个人资料，管理员也可以编辑。
| 必须记录管理员的编辑操作
|===

==== 审计访问
如上例所示，访问控制规则应明确哪些访问需要记录。
例如，如果超级用户或管理员可以编辑他人的个人资料，就应该记录此操作。其他示例还包括检测到的违规行为或试图违反访问控制机制的行为。

=== 使用间接引用
虽然应用中并不常见，但你可以使用*间接*引用。在这种情况下，服务器可以对引用使用哈希、编码或其他函数，使客户端看到的 ID 与服务器实际处理的引用不同。这会降低一些效率（这是安全性与效率之间常见的权衡），并且仍可能被猜测、暴力破解或逆向分析。

这种方法不应作为唯一防护措施，但可以作为额外的一层防护。服务器必须实现客户端（间接）引用到服务器（直接）引用的映射逻辑。

=== 访问控制与 API
许多 API 或 RESTful 端点依赖隐蔽性、静态“密钥”或用户缺乏想象力来控制访问。
