== 刷新令牌

=== 简介

本节将介绍如何刷新访问令牌。

=== 令牌类型

一般有两种令牌：访问令牌和刷新令牌。访问令牌用于向服务器发起 API 调用。访问令牌的有效期有限，因此需要刷新令牌。访问令牌失效后，可以向服务器提交刷新令牌，以获取新的访问令牌。刷新令牌也会过期，但有效期更长。这样用户就无需再次使用凭据进行身份验证。是否需要使用访问令牌和刷新令牌取决于具体情况。选择令牌类型时，可以参考以下几点。

正常流程如下：

```
curl -X POST -H -d 'username=webgoat&password=webgoat' localhost:8080/WebGoat/login
```

服务器返回：

```
{
    "token_type":"bearer",
    "access_token":"XXXX.YYYY.ZZZZ",
    "expires_in":10,
    "refresh_token":"4a9a0b1eac1a34201b3c5659944e8b7"
}
```

如你所见，刷新令牌是随机字符串，服务器可以跟踪它（保存在内存或数据库中），以便将它与获发该令牌的用户关联起来。
因此，只要访问令牌仍然有效，此时可以认为会话是“无状态”的：令牌自包含，服务器无需建立用户会话。
访问令牌失效后，服务器需要查询已存储的刷新令牌，确认它未被禁用。

攻击者获取访问令牌后，该令牌只在一定时间内有效（例如 10 分钟）。之后，攻击者需要刷新令牌才能获得新的访问令牌。因此刷新令牌需要得到更好的保护。
也可以将刷新令牌设计成无状态的，但这样更难判断用户是否已撤销令牌。
服务器完成所有验证后，必须向客户端返回新的刷新令牌和新的访问令牌。客户端可以使用新的访问令牌发起 API 调用。

=== 应检查什么？

无论选择哪种方案，服务器端都应存储足够的信息，以验证用户是否仍可信。可以考虑存储 IP 地址、跟踪刷新令牌的使用次数（如果在访问令牌有效期内多次使用同一个刷新令牌，可能意味着发生了异常行为；此时可以撤销所有令牌并要求用户重新身份验证）。
此外，还要跟踪访问令牌与刷新令牌之间的对应关系，否则攻击者可能利用自己的刷新令牌为其他用户获取新的访问令牌（有关此攻击的详细分析，请参阅 https://emtunc.org/blog/11/2017/jwt-refresh-token-manipulation/）。
还可以检查用户的 IP 地址或地理位置。如果需要发放新令牌，应检查位置是否保持不变；如果发生变化，则撤销所有令牌并要求用户重新进行身份验证。

=== 是否需要刷新令牌？

现代单页应用（SPA）是否有必要使用刷新令牌？正如“存储令牌”一节所述，有两种方案：Web 存储或 Cookie。刷新令牌与访问令牌会存储在一起，因此如果访问令牌泄露，刷新令牌很可能也会被攻陷。不过两者通常有区别：发起 API 调用时会发送访问令牌；只有在需要获取新访问令牌时才发送刷新令牌，而且通常会发送到不同的端点。如果最终访问的是同一服务器，你也可以选择只使用访问令牌。

如前所述，使用访问令牌和单独的刷新令牌，可以让服务器避免反复检查访问令牌：仅在用户需要新访问令牌时执行检查。
当然，也可以只使用访问令牌。服务器需要保存与刷新令牌相同的信息，参见上一段。这样每次都需要检查令牌，但对某些应用而言可能适用。如果将刷新令牌存储起来用于验证，也必须保护好这些令牌（至少使用哈希函数将其存储在数据库中）。

=== JWT 是好选择吗？

有很多资料质疑在客户端与服务器身份验证中相较于 Cookie 使用 JWT 的合理性。JWT 最适合用于服务器之间的通信。在普通 Web 应用中，最好使用传统 Cookie。更多信息请参阅：
