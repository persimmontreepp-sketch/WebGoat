== 其他实现陷阱

前两个练习展示了手写验证代码中缺少的检查。以下是现实中的 WebAuthn 和通行密钥实现中发现的其他错误。

=== 注册

* *账户由客户端指定。* 请求结束阶段根据用户名、电子邮件地址或用户句柄来确定账户，而不是依据服务器端的流程状态。（练习 1）
* *用户句柄可预测或包含个人信息。* 用户句柄若采用用户名或数据库 ID，会向所有能够读取身份验证器的人泄露信息，也更容易被用于针对账户发动攻击。
* *添加密钥前未重新验证。* 攻击者窃取会话 Cookie，或在无人看管的解锁计算机前停留几秒，就可以添加自己的通行密钥，并在密码重置后继续访问。应要求用户近期重新登录，并在添加凭据后通过电子邮件通知用户。
* *凭据 ID 不唯一。* 如果某凭据 ID 已注册到其他账户，就必须拒绝该 ID。
* *信任客户端报告的详细信息。* `authenticatorAttachment` 和 `getTransports()` 都由客户端报告。如果策略规定“仅允许硬件安全密钥”，就需要通过 FIDO 元数据服务验证证明。
* *接受了未请求的算法或格式错误的密钥。* 手写 CBOR/COSE 解析逻辑如果接受任意算法或不验证密钥，就可能使攻击者伪造签名。

=== 身份验证

* *缺少 challenge、challenge 非一次性，或保存在客户端*（例如 Cookie 或未签名令牌中）。捕获的断言可被重放。（练习 2）
* *未检查来源或 RP ID 哈希。* 如果不检查，代理 WebAuthn 流程的钓鱼网站就能获取真实网站会接受的断言，这会让 WebAuthn 失去最主要的优势。同时要小心，不要接受任意子域名或 `http://` 来源。
* *凭据未绑定到用户。* 服务器使用凭据 ID 指向的凭据验证签名，却使用表单中的用户名登录。这样，任何有效密钥都能访问任意账户。
* *无密码登录时未强制 UV。* UP 只能证明*有人*触碰了密钥。密钥丢失或被盗就等于账户失陷。
* *忽略实现了签名计数器的身份验证器所提供的计数器。* 这会失去检测克隆密钥的能力。
* *用户枚举。* 对任何用户名都返回 `allowCredentials`，会让攻击者知道哪些账户存在以及它们拥有哪些凭据。请使用可发现凭据，或对未知用户返回一致的伪造数据。

=== 账户的其他部分

* *恢复方式和回退方式薄弱。* 如果攻击者仍可通过密码、短信验证码或“丢失密钥”电子邮件链接登录，WebAuthn 就无法保护账户。账户安全级别取决于最弱的登录方式。
* *会话处理。* 流程成功后仍需遵循常规规则：使用新的会话 ID、安全 Cookie 并设置超时。
